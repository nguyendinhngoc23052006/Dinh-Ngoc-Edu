# supabase/ — local wiring

- `config.toml` is generated by `npx supabase init` — never hand-write it. Edit only known keys (`[db.seed]`, declared functions/buckets). Leave top-level `project_id` as the folder name: it's a local label, not the remote Project ID.
- Every Edge Function needs its own `[functions.<name>]` block in `config.toml` — the Supabase→GitHub integration deploys ONLY declared functions, so an undeclared one is never pushed to the project and invoking it fails in the browser with `Failed to send a request to the Edge Function` (supabase-js `FunctionsFetchError`, a CORS-less unreachable response). `complete-lesson` shipped without its block and was silently never deployed (2026-06); the bug looks client-side but the fix is the config block.
- `migrations/`: one `YYYYMMDDHHMMSS_description.sql` (UTC) per change, timestamped later than the newest. Never edit a merged migration — add a new one (fix-forward). Every new table ships with its RLS in the same file.
- `seed.sql` must stay idempotent. The baseline migration enables pgcrypto so `crypt()` is available when seeding auth users later.
- `functions/extract-material` runs at upload time (caller's JWT, synchronous): extracts a material's text to `<storage_path>.md` and records the outcome on `course_materials.extract_status`. Shared parsing lives in `functions/_shared/extract.ts`.
- `functions/generate-course` runs with the **caller's JWT** (no service-role key): the owner RLS policies authorize all pipeline writes, so it can only fill courses the caller owns. Heavy work goes through `EdgeRuntime.waitUntil` (202 first, client polls `courses.status`); pure logic stays in `pipeline.ts` so vitest can test it without Deno.
- `clone_course()` copies questions with an EXPLICIT column list — adding a column to `questions` (or chapters/nodes) silently drops to the default on clones unless you also `create or replace` the function (fix-forward) to add the column to both its insert list and select. (Phase 2 added `questions.difficulty` this way.)
- `seed.sql` hand-seeds a full demo course (fixed id `c0000000-…`, owned by the demo user, covering all four question kinds incl. `calc`) so a fresh preview branch is explorable. Like `clone_course`, it lists `courses`/`chapters`/`nodes`/`questions` columns explicitly — a new NOT NULL column or tightened CHECK on those tables must be reflected here too, or the seed INSERT fails on every new preview branch (seed runs on branch creation, so the break only shows there, not in the sandbox). It's idempotent via delete-then-insert on the fixed course id (cascade clears children).
- `functions/delete-account` hard-deletes the caller's account: it derives the user id from the caller's JWT (`getUser()`, never the request body — that's the IDOR guard) and calls `admin.auth.admin.deleteUser` with the service role. It deletes NO rows itself — it relies entirely on every user/owner table referencing `auth.users(id) ON DELETE CASCADE`. So any NEW user-owned table MUST declare `on delete cascade`, or account deletion fails with an FK violation (or orphans rows). All four functions still duplicate `corsHeaders`+`json` (a `_shared/http.ts` extraction is owed as a stand-alone refactor, deliberately kept out of feature PRs).
- To expose ONE column of an own-row-only table to others, don't add a public SELECT policy (RLS policies aren't column-scoped, so that leaks every column — e.g. `profiles.credits`). Instead add a projection VIEW selecting only the safe columns and `grant select` it to anon/authenticated; the view runs with its owner's rights (not `security_invoker`), so it bypasses the base RLS but can reveal only what it projects. `public_profiles` does this for `(user_id, display_name)`, scoped to public-course authors. Separately, `profiles` revokes blanket UPDATE and grants per-column, so any new client-writable column needs its own `grant update (col) on public.profiles to authenticated` (display_name, like pet_enabled/pet_cheers_enabled).
