- AI calls use the Gemini native `generateContent` API (not the OpenAI-compat wrapper), chosen by Edge Function secrets (`AI_API_KEY`/`AI_BASE_URL`/`AI_MODEL`, default `gemini-2.5-flash`). Thinking tokens are capped per-call via `generationConfig.thinkingConfig.thinkingBudget`. `responseSchema` accepts only the **OpenAPI 3.0 subset** — keywords like `additionalProperties`, `$schema`, `$ref`, `patternProperties`, `definitions`, and the Gemini extension `propertyOrdering` are rejected with a 400; a regression test in `pipeline.test.ts` enforces this. `description`, `minItems`, and `maxItems` ARE in the subset, BUT `minItems` on a top-level array is a **silent killer** on 2.5 Flash: when the model cannot meet the floor it returns an empty `questions: []` (or a truncated body), no error — that was the root cause of the "22 lessons / 1 question total" failure mode. Treat `minItems` as forbidden in question schemas; enforce minimum counts in the validator + a retry pass instead. Post-call validators (`validateSyllabus`, `validateNodeQuestions`) are the real enforcement layer that drops unknown fields. **`thinkingBudget` is binary on 2.5 Flash:** any value from 1–1023 is silently promoted to 1024 internally; the only real choice is `0` (disabled) vs any positive value (thinking on). Use `1024` explicitly for clarity; `0` only on retries where the initial call already thought through the problem.

- Question generation is **one Gemini call PER LESSON** (`generateLessonQuestions`), not per-chapter batch. Chapters still run in PARALLEL via `Promise.all(syllabus.map(generateChapter))`; lessons within a chapter run SEQUENTIALLY so the chapter's stable-prefix prompt benefits from Gemini's implicit cache (1024-token min, 75% off cached input on 2.5 family, ~5 min TTL). Each call asks for `QUESTIONS_PER_NODE = 8` mcq/mcq_multi/fill_blank questions with a tiny schema (`NODE_QUESTIONS_SCHEMA`): no `minItems` anywhere, no `node_index`, no `calc` (calc comes from a separate follow-up — see below). A lesson that comes back below `MIN_QUESTIONS_PER_NODE = 5` gets ONE focused retry asking for exactly the missing count with existing prompts listed so the model can't duplicate; the retry is SKIPPED when `Date.now() > deadline`. Pipeline budget `MAX_PIPELINE_MS = 12 min` (under the 15-min `STALE_PROCESSING_MS` reclaim window); per-call `DEFAULT_REQUEST_TIMEOUT_MS = 50 s`, `QUESTION_REQUEST_TIMEOUT_MS = 55 s`. Chapter loop uses a non-throwing deadline check that fills empty buckets and breaks — a throw mid-loop would wipe the chapter's already-generated questions because the bulk insert runs AFTER the loop. Partial completion flips to `ready` and surfaces a "N lesson(s) need a retry" summary in `generation_error`; the CoursePage banner offers a one-tap "Fill incomplete lessons" targeted repair (see repair-path entry below). **Why this shape vs the previous chapter-batch:** the batch asked for 50 questions (10/node × 5 nodes) with `responseSchema.minItems: 30` and a nested calc spec — Flash 2.5 silently truncated/emptied the response, bare `catch {}` ate the failure, and a real course landed with 1 question across 22 lessons. Per-lesson calls are small, land reliably, and surface their errors.
- **Calc questions get a dedicated per-lesson follow-up call** (`generateLessonQuestions` after the main mcq/fill_blank pass): gated by `detectFormulas(lessonSource) && Date.now() + 30_000 < deadline`. Uses `CALC_QUESTIONS_SCHEMA` (calc-only — no kind enum to decide, only the calc shape) and `buildCalcQuestionsPrompt` with six few-shots covering single-formula, multi-step `steps[]`, piecewise ternary, log/sqrt, series via `sigma`, and combinatorics via `binom_pmf`. The prompt has an explicit "return `{"questions":[]}` if the source has no usable formula" escape, so the empty response is valid (no `minItems`). Calc failure is silently swallowed — calc is **additive bonus**, the lesson keeps its mcq/fill_blank questions. `CALC_QUESTIONS_PER_NODE = 2`, `CALC_FOLLOWUP_TIMEOUT_MS = 25_000`. Worst-case math chapter: 5 lessons × (35 + 35 + 25 s) ≈ 8 min, fits the 10-min budget via the deadline check.
- **Calc DSL — the safe `calc.ts` parser** is recursive-descent → AST → evaluator, no `eval`. Every callable is whitelisted in the `FUNCTIONS` registry: arithmetic (+ − × ÷ % ^), comparison, logical, ternary, ~50 functions (abs/sign/min/max/sqrt/pow/log family/trig/hyperbolic/rounding/factorial/choose/perm/gcd/lcm/sum/prod/mean/median/variance/stdev/binom_pmf/binom_cdf/normal_pdf/normal_cdf/poisson_pmf/poisson_cdf), and four specials (`sigma(lo,hi,body)` binds `i`; `pi_iter(lo,hi,body)` binds `i`; `iterate(init,count,body)` binds `x`; `cases(c1,v1,...,default)`). Constants `pi`, `e`. Hard bounds: `MAX_ITERATIONS = 10_000`, `MAX_EXPRESSION_DEPTH = 200`, `MAX_FORMULA_CHARS = 500`. Specs use `variables[]` (ranges + decimals) + optional `steps[]` (ordered named bindings; step name can't shadow a variable or function/constant) + final `formula`. **Re-validate before evaluating a DB-sourced spec**: `complete-lesson` (via `grade.ts`) calls `validateCalcSpec(question.calc)` before `gradeCalc`, so a tampered row gets rejected at midpoint-sample evaluation instead of burning 10K iterations per regrade. Generation-time validation is via `validateNodeCalcQuestions` → `validateCalcSpec`. **`pi_iter` not `pi`** — the constant takes the name; the iteration primitive is `pi_iter`.
